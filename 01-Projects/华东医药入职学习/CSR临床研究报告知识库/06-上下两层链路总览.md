# 上下两层链路总览

## 核心框架

围绕 CSR 的知识可以拆成两层：

1. **上层业务证据链路**：解释一项研究为什么做、怎么推进、由谁完成、最终如何形成 CSR。
2. **下层数据标准链路**：解释临床数据从哪里来、如何变可信、如何被标准化、分析并支持 CSR 和监管递交。

这两个层次不是割裂的。上层决定“要证明什么”，下层保证“证明材料可信、标准、可审评”。

## 上层：业务证据链路

### 关注的问题

- 这个新药或新适应症为什么值得做？
- 临床开发策略是什么？
- 单项试验如何设计？
- 哪些部门在什么时间点参与？
- 研究结束后如何形成 CSR？
- CSR 如何支持注册申报和业务决策？

### 简化链路

`研发假设/适应症机会 → 临床开发策略 → Protocol/SAP → 试验执行 → 数据分析 → CSR → 注册/决策`

### 典型角色

| 节点 | 主要角色 | 关键产出 |
|---|---|---|
| 研发假设/适应症机会 | 医学、临床科学、转化医学、商业、注册 | 立项判断、疾病和竞品分析 |
| 临床开发策略 | Clinical Lead、统计、注册、安全、运营 | 临床开发计划、关键研究路径 |
| Protocol/SAP | 临床、统计、医学写作、数据管理、安全 | Protocol、SAP、TFL shell |
| 试验执行 | PI、CRC、CRA、PM、药物警戒 | 入组、访视、给药、安全上报、源文件 |
| 数据分析 | 数据管理、统计、程序员、临床 | 锁库数据、分析数据集、TFL |
| CSR | 医学写作、临床、统计、安全、注册、QA | CSR 定稿、审阅记录、附录 |
| 注册/决策 | 注册、临床、医学、安全、管理层 | 申报资料、获益风险判断、后续研发决策 |

## 下层：数据标准链路

### 关注的问题

- 数据的源头在哪里？
- eCRF/EDC 如何保证数据完整和可追溯？
- Query、Edit Check、Audit Trail 分别解决什么问题？
- 为什么要数据库锁定？
- SDTM、ADaM、TFL 如何支持 CSR？
- Define-XML 和标准化数据递交在 CSR 后面扮演什么角色？

### 简化链路

`源数据/eSource → eCRF/EDC → Query/Edit Check/Audit Trail → DBL → SDTM → ADaM → TFL → CSR → Define-XML/标准化数据递交`

### 典型角色

| 节点 | 主要角色 | 关键产出 |
|---|---|---|
| 源数据/eSource | 研究者、CRC、受试者、实验室、设备系统 | 病历、检查结果、电子源数据 |
| eCRF/EDC | 研究中心、数据管理、EDC 构建团队 | eCRF 数据、录入规则、权限和审计轨迹 |
| Query/Edit Check | 数据管理、CRA、研究中心 | 数据疑问、清理记录、质量问题闭环 |
| DBL | 数据管理、统计、临床、安全 | 锁库确认、冻结数据库 |
| SDTM | 数据标准/统计编程 | 递交用标准化数据 |
| ADaM | 统计、统计编程 | 分析数据集 |
| TFL | 统计、统计编程、QC | 表、图、列表 |
| CSR | 医学写作、临床、安全、统计 | 结果叙述和医学解释 |
| Define-XML/递交 | 数据标准、统计编程、注册 | 数据说明文件、标准化申报数据包 |

## 两层之间的连接点

| 上层业务问题 | 下层数据支撑 |
|---|---|
| Protocol 定义终点和访视 | eCRF 需要采集对应字段 |
| SAP 定义分析方法 | ADaM 需要生成可分析变量 |
| 临床团队解释疗效 | TFL 需要提供清晰、可追溯结果 |
| 安全团队判断风险 | AE/SAE 数据需要标准编码和及时上报 |
| CSR 写作形成结论 | 数据、分析、偏离和安全性都要可追溯 |
| 注册递交接受审评 | SDTM、ADaM、Define-XML 需要符合监管要求 |
