# 下层数据层与数仓建设思路

## 定位

下层数据层关注的是：

`源数据/eSource → eCRF/EDC → Query/Edit Check/Audit Trail → DBL → SDTM → ADaM → TFL → CSR → Define-XML/标准化数据递交`

这条链路适合搭建临床数仓，因为它天然围绕：

- 数据来源
- 字段标准
- 数据质量
- 版本追溯
- 分析口径
- 监管递交
- CSR 引用

## 数仓建设目标

临床数仓不是简单把 EDC 数据搬进数据库，而是要支持三个目标：

1. **可信**：知道数据从哪里来、谁改过、什么时候锁定。
2. **标准**：能对齐 CDISC、受控术语、分析数据集和递交要求。
3. **可用**：能支持项目监控、统计分析、CSR 写作、注册递交和 AI 辅助。

## 建议的数据分层

| 层级  | 对应链路                        | 主要内容                        | 价值            |
| --- | --------------------------- | --------------------------- | ------------- |
| 原始层 | 源数据/eSource、EDC 导出          | 原始 eCRF、实验室、影像、安全、合并用药、访视数据 | 保留原貌，支持追溯     |
| 清洗层 | Query/Edit Check、数据清理       | 缺失、异常、一致性、query 状态、数据清理版本   | 支持数据质量管理      |
| 标准层 | SDTM、Controlled Terminology | SDTM domain、受控术语、标准变量、单位转换  | 支持标准化递交和跨研究比较 |
| 分析层 | ADaM、SAP                    | 分析集、派生变量、终点算法、分析口径          | 支持统计分析和 TFL   |
| 报告层 | TFL、CSR                     | 表图列表、CSR 引用、章节结果摘要          | 支持医学写作和审阅     |
| 递交层 | Define-XML、申报数据包            | 数据说明、元数据、验证规则、递交包状态         | 支持监管递交        |

## 核心数据对象

### 1. 研究主数据

- 研究编号
- 适应症
- 药物/产品
- 试验阶段
- 申办方
- 国家/中心
- 研究设计
- 治疗组
- 关键日期

### 2. 受试者主线

- 筛选
- 入组
- 随机
- 给药
- 访视
- 完成/退出
- 分析集归属

### 3. 采集字段和 eCRF 元数据

- 表单
- 字段
- 数据类型
- 单位
- 访视
- 必填规则
- edit check 规则
- 字段来源

### 4. 数据质量和追溯

- query
- edit check
- audit trail
- 数据修改记录
- 锁库状态
- 数据清理版本
- issue 和闭环状态

### 5. CDISC 标准映射

- CDASH 字段
- SDTM domain
- SDTM variable
- ADaM dataset
- ADaM variable
- controlled terminology
- Define-XML metadata

### 6. 分析和报告对象

- SAP 分析方法
- TFL shell
- TFL 输出
- CSR 章节
- CSR 引用表号
- 结果摘要
- 审阅意见

## 和 AI 的关系

如果没有数据层，AI 只能基于文档“读和写”。有了数据层，AI 才能做更可靠的辅助：

- 从标准字段中抽取 CSR 所需信息
- 自动生成项目数据质量摘要
- 检查 protocol、SAP、TFL、CSR 的一致性
- 基于 TFL 元数据生成结果草稿
- 回溯每个结论对应的数据来源

关键原则是：**AI 输出必须能追溯到数据、文件或标准定义。**

## 优先建设顺序

### 第一阶段：资料和字段目录

- 建立 EDC、CDISC、ICH、CSR 相关资料清单。
- 建立术语表和字段字典。
- 梳理常见文件：Protocol、SAP、TFL、CSR、Define-XML。

### 第二阶段：研究级元数据

- 建立研究维度、中心维度、受试者维度、访视维度。
- 把研究设计、治疗组、关键时间点结构化。
- 建立文档和数据对象之间的引用关系。

### 第三阶段：EDC 到 SDTM/ADaM 映射

- 梳理 eCRF 字段到 SDTM domain/variable 的映射。
- 梳理 SDTM 到 ADaM 的派生逻辑。
- 管理受控术语、单位、日期和缺失值口径。

### 第四阶段：TFL/CSR 报告层

- 建立 TFL 元数据：表号、标题、分析集、数据来源、对应 CSR 章节。
- 建立 CSR 章节和 TFL 的引用关系。
- 支持自动生成结果摘要和一致性检查。

### 第五阶段：递交和合规视角

- 接入 Define-XML、验证规则、递交包状态。
- 建立审计、版本、权限和数据血缘。
- 对齐 NMPA/FDA/ICH/CDISC 的要求。

## 数仓设计时要避免的误区

- 只存 EDC 原始表，不管理标准化映射。
- 只关注业务报表，不保留数据血缘。
- 只做项目级数据，不抽象跨研究标准。
- 只服务统计，不考虑 CSR 和注册递交。
- 只让 AI 读文档，不让 AI 连接结构化来源。

## 和上层业务链路的关系

上层业务链路会提出问题：

- 这个研究的主要终点是什么？
- 哪些受试者进入主要分析集？
- 安全性结果是否支持获益风险判断？
- CSR 某句话引用了哪张 TFL？

下层数据仓库要能回答：

- 这个终点来自哪个 protocol/SAP 定义？
- 这个分析集来自哪个 ADaM 数据集和规则？
- 这个安全性结果来自哪个 AE 数据和编码版本？
- 这个 CSR 结论能追溯到哪张表、哪个数据集、哪个字段？
