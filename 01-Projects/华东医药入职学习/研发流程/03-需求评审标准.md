# 需求评审标准

## 1. 目的

需求评审的目的不是“产品讲一遍 PRD”，而是让业务、产品、研发、测试、设计等相关方在开发前完成一致确认。

一句话：需求评审是开发前的“共识确认会”和“风险识别会”。

## 2. 适用范围

适用于所有进入研发开发的产品需求，包括：

```text
1. 新功能需求
2. 功能优化需求
3. 流程调整需求
4. 权限变更需求
5. 数据报表需求
6. 审批流需求
7. 系统集成需求
8. 合规、审计、风控类需求
```

## 3. 评审类型

| 类型 | 适用场景 | 参与人 |
|---|---|---|
| 轻量评审 | 小改动、低风险需求 | 产品、研发、测试 |
| 标准评审 | 常规产品需求 | 产品、业务、研发、测试、设计 |
| 专项评审 | 高风险、跨系统、合规、数据类需求 | 产品、业务、研发、测试、架构、数据、安全、合规 |
| 二次评审 | 首次评审未通过或重大变更 | 原评审参与人 |

## 4. 评审准入标准

| 准入项 | 标准 |
|---|---|
| 需求已准入 | 已进入需求池，有需求编号 |
| PRD 已完成 | 背景、目标、范围、规则、验收标准齐全 |
| 原型已完成 | 页面、入口、操作、状态表达清楚 |
| 业务流程已明确 | 主流程、分支流程、异常流程清楚 |
| 权限规则已明确 | 不同角色能看什么、做什么 |
| 数据规则已明确 | 字段、口径、统计逻辑清楚 |
| 验收标准已完成 | 可被测试和业务验证 |
| 待确认问题已列出 | 未确认事项不能隐藏 |

## 5. 评审参与角色与职责

| 角色 | 核心职责 |
|---|---|
| 产品经理 | 讲清背景、目标、范围、方案、验收标准 |
| 业务负责人 | 确认业务场景、规则、价值和上线可用性 |
| 研发负责人 | 判断技术可行性、工作量、依赖和风险 |
| 测试负责人 | 识别测试范围、异常场景、验收口径 |
| UI/UX | 确认交互体验、页面一致性和可用性 |
| 数据/BI | 确认数据口径、指标、埋点和报表逻辑 |
| 架构/安全/合规 | 参与高风险需求评审 |
| 项目负责人 | 确认资源、排期、里程碑和风险闭环 |

## 6. 评审前准备标准

产品经理至少提前 1 个工作日发送评审材料；复杂需求提前 2-3 个工作日。

必发材料：

```text
1. PRD 文档
2. 原型图
3. 业务流程图
4. 字段与数据规则表
5. 权限规则表
6. 验收标准
7. 待确认问题清单
```

高风险需求额外材料：

```text
1. 状态流转图
2. 数据口径说明
3. 接口依赖清单
4. 影响范围说明
5. 灰度和回滚初步方案
6. 合规或安全确认事项
```

## 7. 评审会议议程

```text
1. 产品说明需求背景和业务目标
2. 产品说明本期范围和不做范围
3. 产品演示原型和核心流程
4. 产品说明关键规则、权限、状态和异常场景
5. 业务确认场景和规则是否正确
6. 研发确认技术可行性、依赖、风险和工作量
7. 测试确认测试范围、验收标准和风险点
8. 设计确认交互和视觉问题
9. 项目负责人确认排期、资源和里程碑
10. 输出评审结论和行动项
```

## 8. 评审必须确认的 10 件事

```text
1. 为什么做：业务问题是否真实存在，目标是否明确。
2. 做什么：本期范围和不做范围是否清楚。
3. 给谁用：使用、查看、审批、管理角色是否清楚。
4. 怎么用：入口、主流程、分支流程、异常流程是否完整。
5. 规则是什么：字段、校验、状态、审批、计算、导入导出、通知规则是否明确。
6. 权限怎么控：菜单、页面、按钮、数据、字段、导出、审批权限是否明确。
7. 数据怎么算：指标定义、统计周期、数据来源、过滤条件、更新频率、历史数据处理是否明确。
8. 异常怎么办：空数据、无权限、重复提交、接口失败、数据超限等是否明确。
9. 如何验收：测试、产品、业务、上线后指标是否明确。
10. 风险和依赖是什么：系统依赖、数据清洗、权限配置、第三方接口、历史数据、培训等是否明确。
```

## 9. 评审结论标准

| 结论 | 标准 | 后续动作 |
|---|---|---|
| 通过 | 目标、范围、规则、验收标准基本明确 | 进入开发排期 |
| 有条件通过 | 存在少量问题，但不影响整体方案 | 产品补充材料后进入开发 |
| 重新评审 | 核心规则、范围、方案、数据口径不清 | 修改后重新开评审 |
| 暂缓 | 价值不足、资源不足、时机不合适 | 回到需求池 |
| 不通过 | 需求不成立或方案不可行 | 关闭或重做方案 |

## 10. 评审通过标准

```text
1. 业务负责人确认业务场景和规则。
2. 产品负责人确认需求范围和验收标准。
3. 研发负责人确认技术可行性。
4. 测试负责人确认可测试。
5. 关键风险已有处理方案。
6. 待确认问题不影响开发启动。
7. 排期或工作量评估可以启动。
```

## 11. 必须重新评审的情况

```text
1. 需求目标发生变化。
2. 本期范围明显扩大。
3. 核心流程发生变化。
4. 权限规则发生变化。
5. 数据口径发生变化。
6. 状态流转发生变化。
7. 涉及金额、合同、审批、合规规则变化。
8. 技术方案变化导致用户体验或业务流程变化。
9. 预计排期增加超过原计划 30%。
```

## 12. 不同行业评审重点

| 行业 | 重点看 | 高风险点 |
|---|---|---|
| 互联网 | 用户路径、转化链路、埋点、活动时效、异常状态 | 登录、支付、下单、活动、推送、推荐策略 |
| SaaS / B 端 | 组织架构、角色权限、多租户隔离、客户配置差异、导入导出 | 客户定制转通用功能时影响其他客户 |
| 金融 | 金额计算、资金安全、审批权限、操作留痕、监管报送、数据一致性 | 金额错误、权限越权、审计链路缺失 |
| 医疗 / 医药 | 流程合规、研发/临床/质量节点、数据准确性、审批留痕、版本追溯 | 关键审批缺失、数据口径错误、记录不可追溯 |
| 制造 / ERP | 主数据准确性、库存口径、采购流程、生产计划、成本核算 | 库存、成本、单据状态和历史数据处理 |

## 13. 会议纪要标准

评审结束后，产品经理应在当天输出会议纪要。

会议纪要必须包含：

```text
会议时间：
需求编号：
需求名称：
参会人员：
评审结论：
确认事项：
待办事项：
风险事项：
变更事项：
下次节点：
```

待办事项格式：

| 待办事项 | 责任人 | 截止时间 | 是否影响开发 | 状态 |
|---|---|---|---|---|
| 补充导出字段上限规则 | 产品经理 | 7月10日 | 是 | 待完成 |
| 确认历史数据处理方式 | 业务负责人 | 7月10日 | 是 | 待完成 |
| 评估接口性能风险 | 研发负责人 | 7月11日 | 否 | 待完成 |

## 14. 管理要求

```text
1. 未完成 PRD 和验收标准的需求，不允许正式评审。
2. 评审未通过的需求，不允许进入开发。
3. 评审结论必须当天记录。
4. 所有待办事项必须有责任人和截止时间。
5. 涉及范围、权限、流程、数据口径变化，必须重新评审。
6. 业务负责人未确认的业务规则，不允许开发。
7. 测试负责人未确认验收口径的需求，不允许提测。
8. 高风险需求必须有灰度、回滚或应急方案。
```
