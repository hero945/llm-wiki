# 业务验收标准

## 1. 目的

业务验收的核心不是确认“功能有没有做出来”，而是确认“这个功能能不能真正支撑业务使用”。

一句话：测试验收看“质量是否达标”，业务验收看“业务是否可用”。

## 2. 适用范围

适用于：

```text
1. 新功能上线
2. 核心流程调整
3. 审批流调整
4. 报表和数据看板
5. 权限和角色调整
6. 客户交付类需求
7. 业务规则变更
8. 运营、销售、财务、供应链、研发等内部系统需求
```

## 3. 验收基本原则

### 3.1 业务场景优先

业务验收不能只看页面，而要回到真实业务场景。

示例：

```text
不是只问：导出按钮能不能点？
而是要问：销售主管是否能用这份导出数据完成每周客户跟进管理？
```

### 3.2 业务负责人确认制

业务验收必须有明确业务负责人确认，不能由产品经理代替业务方做最终业务确认。

建议规则：

```text
1. 单部门需求：由该部门负责人或指定业务代表验收。
2. 跨部门需求：由主责部门负责人牵头，多部门共同确认。
3. 客户交付需求：由客户成功/销售/交付负责人确认。
4. 合规或财务类需求：由合规、财务或审计负责人确认。
```

### 3.3 按验收标准验收，不靠主观感觉

验收必须围绕：

```text
原始业务问题
PRD 目标
核心业务流程
业务规则
数据口径
权限规则
上线使用条件
```

## 4. 业务验收准入标准

| 准入项 | 标准 |
|---|---|
| 测试验收通过 | 无阻断级 Bug |
| 产品走查完成 | 产品确认符合 PRD |
| 核心流程可用 | 主流程、关键分支流程已验证 |
| 测试环境或预发环境可用 | 业务方可以操作 |
| 测试账号准备完成 | 不同业务角色账号可用 |
| 测试数据准备完成 | 数据接近真实业务场景 |
| 验收清单准备完成 | 产品提供明确验收项 |
| 已知问题已说明 | 不影响验收的问题提前告知 |

## 5. 业务验收参与角色

| 角色 | 职责 |
|---|---|
| 产品经理 | 组织验收、讲解范围、记录问题 |
| 业务负责人 | 判断是否满足业务目标和规则 |
| 业务代表/一线用户 | 验证真实使用场景 |
| 测试负责人 | 说明测试结论和剩余风险 |
| 研发负责人 | 解释技术限制、评估问题修复 |
| 项目负责人 | 协调上线条件和时间 |

## 6. 业务验收内容

### 6.1 原始问题是否解决

必须回看需求最初提出时的问题：

```text
1. 当初为什么要做这个需求？
2. 当前功能是否解决了原始问题？
3. 是否只是做了功能，但问题仍然存在？
4. 是否出现了新的业务成本？
```

### 6.2 业务流程是否可用

业务方应按真实工作流程操作。

验收重点：

```text
1. 操作顺序是否符合业务习惯？
2. 是否遗漏关键业务节点？
3. 是否需要额外线下沟通？
4. 是否能支撑完整闭环？
5. 异常情况是否能处理？
```

### 6.3 业务规则是否正确

重点确认业务规则和真实管理规则一致。

```text
1. 字段含义是否正确？
2. 计算逻辑是否正确？
3. 审批规则是否正确？
4. 状态变化是否正确？
5. 提醒和通知是否正确？
6. 操作限制是否符合业务要求？
```

### 6.4 数据口径是否一致

报表、看板、导出、统计类需求必须重点验收数据口径。

```text
1. 指标定义是否符合业务认知？
2. 统计周期是否正确？
3. 数据来源是否正确？
4. 过滤条件是否正确？
5. 历史数据是否处理正确？
6. 导出数据是否和页面一致？
```

### 6.5 权限是否符合组织规则

```text
1. 谁能看？
2. 谁能新增？
3. 谁能修改？
4. 谁能删除？
5. 谁能审批？
6. 谁能导出？
7. 谁能查看敏感字段？
```

### 6.6 一线用户是否能使用

建议选择 1-3 名真实使用者参与验收，观察：

```text
1. 是否能找到入口？
2. 是否理解字段含义？
3. 是否知道下一步操作？
4. 是否会误操作？
5. 是否需要培训或说明文档？
```

## 7. 验收结论标准

| 结论 | 标准 | 后续动作 |
|---|---|---|
| 通过 | 满足核心业务流程和上线条件 | 进入上线准备 |
| 有条件通过 | 有小问题，但不影响核心业务使用 | 修复指定问题后上线 |
| 不通过 | 核心业务流程、规则、数据口径不满足 | 退回修改 |
| 暂缓上线 | 功能可用，但业务时机、培训、数据未准备好 | 补齐上线条件 |

## 8. 可以有条件通过的情况

```text
1. 文案细节不影响理解。
2. 样式问题不影响使用。
3. 非核心字段展示顺序调整。
4. 不影响主流程的小体验问题。
5. 低频场景可后续优化。
```

## 9. 必须不通过的情况

```text
1. 核心业务流程无法完成。
2. 业务规则与实际规则不一致。
3. 数据口径错误。
4. 权限范围错误。
5. 审批流程缺失关键节点。
6. 关键字段缺失或含义错误。
7. 一线用户无法完成核心操作。
8. 存在明显合规、财务、数据安全风险。
```

## 10. 不同行业业务验收重点

| 行业 | 重点验收 | 典型问题 |
|---|---|---|
| 互联网 | 用户路径、核心转化链路、活动规则、异常状态、埋点 | 活动规则测试通过，但用户路径太长，转化仍然低 |
| SaaS / B 端 | 客户组织架构、角色权限、业务流程、导入导出、多客户配置 | 功能可用，但客户组织层级复杂，权限无法落地 |
| 金融 | 金额口径、审批权限、风控规则、审计留痕、监管报送口径 | 页面显示正确，但监管口径与财务口径不一致 |
| 医疗 / 医药 | 流程合规、审批记录、研发/临床/质量节点、版本追溯 | 流程能走通，但关键审批记录不可追溯 |
| 制造 / ERP | 库存准确性、采购流程、生产计划、成本核算、主数据一致性 | 采购流程可用，但未同步影响库存占用 |

## 12. 管理要求

```text
1. 未完成测试验收，不进入业务验收。
2. 业务验收必须有业务负责人参与或授权确认。
3. 涉及数据口径的需求，必须由业务负责人确认口径。
4. 涉及权限的需求，必须按角色逐一验收。
5. 业务验收不通过，不允许上线。
6. 有条件通过的问题必须明确是否上线前修复。
7. 业务验收结论必须留痕。
```
