# 需求准入与分级标准

## 1. 目的

建立统一的需求入口和判断标准，避免需求通过口头、微信、临时会议等方式分散流转，导致需求来源不清、价值不明、优先级混乱、研发资源被频繁打断。

本标准用于明确：

```text
什么样的诉求可以进入需求池；
什么样的诉求不能直接进入开发；
需求应该如何分级；
不同等级需求如何响应；
谁有权确认需求优先级。
```

## 2. 适用范围

适用于公司所有涉及产品、系统、平台、工具、数据、流程优化类需求，包括：

```text
1. 新功能需求
2. 功能优化需求
3. 业务流程调整需求
4. 数据报表需求
5. 权限配置需求
6. 系统集成需求
7. 用户体验优化需求
8. 合规、审计、风控类需求
9. 线上问题引发的产品改造需求
```

不适用于纯技术故障修复、服务器运维、临时数据查询等非产品需求。但如果此类问题反复出现，应转化为产品化需求进入需求池。

## 3. 核心原则

### 3.1 统一入口原则

所有需求必须进入统一需求池，不允许只通过口头、微信、邮件、会议纪要直接进入开发。

行业经验：

```text
互联网公司：通过 Jira、禅道、飞书多维表格、TAPD 管理需求。
SaaS 公司：客户需求必须进入 CRM/需求池，避免销售直接推动研发。
金融行业：所有系统变更必须有登记编号和审批记录。
医疗/医药行业：涉及业务规则和数据口径的需求必须可追溯。
```

### 3.2 问题先于方案原则

需求提出方经常会直接说“我要一个按钮”“我要一个报表”“我要一个审批流”。产品经理不能直接按方案接收，而要先还原业务问题。

错误表达：

```text
我要加一个导出按钮。
```

合格表达：

```text
销售主管每周需要统计本部门客户跟进情况，目前需要人工复制整理，耗时约 2 小时，且容易漏掉异常客户，因此希望系统支持按部门导出客户跟进明细。
```

### 3.3 价值决定优先级原则

需求优先级不由提出人的职位、声音大小或催促频率决定，而由业务价值、影响范围、紧急程度、风险程度和实现成本共同决定。

### 3.4 需求可追溯原则

每个进入需求池的需求必须具备唯一编号，后续 PRD、原型、开发任务、测试用例、上线记录、价值复盘都应关联该编号。

示例：

```text
REQ-2026-001 客户跟进清单优化
REQ-2026-002 合同审批权限调整
REQ-2026-003 销售业绩看板新增回款维度
```

## 4. 需求准入标准

一个需求要进入需求池，必须满足以下 5 个基本条件。

| 准入项 | 说明 | 是否必填 |
|---|---|---|
| 需求来源 | 谁提出，来自哪个部门、客户或用户群体 | 必填 |
| 业务场景 | 在什么业务场景下发生 | 必填 |
| 当前问题 | 当前流程、系统或数据存在什么问题 | 必填 |
| 影响范围 | 影响哪些用户、部门、客户、金额或业务量 | 必填 |
| 期望结果 | 做完后希望达到什么效果 | 必填 |

如果以上信息缺失，需求状态应标记为“待补充”，不得直接进入评审或开发。

## 5. 需求登记字段标准

| 字段 | 填写说明 |
|---|---|
| 需求编号 | 自动生成或产品经理维护 |
| 需求标题 | 一句话描述需求 |
| 需求类型 | 新功能/优化/报表/权限/流程/合规/问题改造 |
| 提出人 | 需求提出人 |
| 提出部门 | 所属部门 |
| 提出时间 | 登记日期 |
| 使用角色 | 谁会使用该功能 |
| 业务场景 | 具体使用场景 |
| 当前问题 | 当前痛点或风险 |
| 期望目标 | 希望改善的结果 |
| 影响范围 | 用户数、客户数、订单量、金额、部门等 |
| 期望上线时间 | 如有明确时间要求需填写 |
| 紧急原因 | 为什么急 |
| 替代方案 | 现在是否有人工或系统替代方式 |
| 相关材料 | 截图、表格、流程图、客户反馈等 |
| 初步优先级 | P0/P1/P2/P3 |
| 当前状态 | 待补充/待澄清/待评估/待评审/已排期等 |
| 产品负责人 | 负责跟进的 PM |
| 备注 | 其他说明 |

## 6. 不予准入标准

| 情况 | 处理方式 |
|---|---|
| 只有一句“加个功能” | 退回补充业务场景 |
| 只有个人偏好，没有业务依据 | 暂缓 |
| 已有功能可以解决 | 转为培训或操作说明 |
| 无明确使用对象 | 退回澄清 |
| 无明确问题，只是想尝试 | 进入观察池 |
| 与公司当前目标无关 | 暂缓 |
| 需求与现有规则冲突 | 进入专项评估 |
| 涉及合规/财务/权限风险但无审批人 | 不进入开发 |

## 7. 需求分级标准

| 等级 | 定义 | 响应方式 |
|---|---|---|
| P0 | 线上事故、合规风险、核心业务中断、重大客户阻断 | 立即响应，可打断当前排期 |
| P1 | 影响核心业务流程、关键客户、收入目标或重要管理要求 | 优先排期，进入近期版本 |
| P2 | 有明确提效、体验优化、流程补全价值 | 正常排期 |
| P3 | 低频、局部、锦上添花或价值不明确 | 进入需求池观察 |

### 7.1 P0 需求

满足任一条件即可判定为 P0：

```text
1. 线上核心流程不可用。
2. 造成收入、订单、支付、交付等关键业务中断。
3. 存在重大合规、审计、数据安全风险。
4. 影响核心客户正常使用，并可能导致重大损失。
5. 管理层明确要求立即处理的重大风险事项。
```

### 7.2 P1 需求

满足以下情况可判定为 P1：

```text
1. 影响核心业务效率或收入目标。
2. 影响关键客户交付或续约。
3. 影响多个部门协作。
4. 有明确时间窗口，如客户验收、审计、活动上线。
5. 不处理会导致明显业务损失。
```

### 7.3 P2 需求

满足以下情况可判定为 P2：

```text
1. 有明确提效价值，但不阻断当前业务。
2. 能改善用户体验。
3. 能减少人工操作或降低错误率。
4. 能补齐已有流程中的非关键能力。
5. 有一定用户范围，但紧急程度不高。
```

### 7.4 P3 需求

满足以下情况可判定为 P3：

```text
1. 使用频率低。
2. 影响范围小。
3. 缺少数据或业务价值支撑。
4. 只是个别用户偏好。
5. 当前已有替代方案。
6. 实现成本高但收益不明确。
```

## 8. 需求价值评分模型

| 维度 | 权重 | 评分说明 |
|---|---:|---|
| 业务价值 | 30% | 是否增收、降本、提效、控风险 |
| 影响范围 | 20% | 影响用户、客户、部门或业务量大小 |
| 紧急程度 | 20% | 是否有明确时间窗口 |
| 战略匹配 | 15% | 是否符合公司阶段重点 |
| 实现成本 | 10% | 成本越低分越高 |
| 风险程度 | 5% | 风险越低分越高 |

评分采用 1-5 分：

```text
5 分：非常高
4 分：较高
3 分：中等
2 分：较低
1 分：很低
```

优先级建议：

| 总分 | 建议处理 |
|---:|---|
| 4.0-5.0 | 优先排期 |
| 3.0-3.9 | 正常排期 |
| 2.0-2.9 | 合并、观察或延后 |
| 低于 2.0 | 暂缓或拒绝 |

## 9. 不同行业分级侧重点

| 行业 | 重点关注 | 常见高优先级场景 |
|---|---|---|
| 互联网 | 用户增长、转化率、活跃度、支付链路、活动时效 | 登录失败、支付失败、下单失败、活动页面异常 |
| SaaS / B 端 | 客户续费、关键客户交付、权限体系、数据报表 | 大客户验收阻塞、核心流程无法闭环 |
| 金融 | 资金安全、权限隔离、审计留痕、监管合规 | 金额计算错误、审批权限异常、监管报送口径错误 |
| 医疗 / 医药 | 数据准确性、流程合规、审批留痕、质量管理 | 审批记录不可追溯、敏感研发数据暴露 |
| 制造 / ERP | 生产流程、库存准确性、采购交付、成本核算 | 库存数据不准、采购审批阻塞、成本计算错误 |

## 10. 管理要求

```text
1. 未进入需求池的需求，不允许进入开发。
2. 未说明业务场景的需求，不允许进入评审。
3. 未完成优先级判断的需求，不允许排期。
4. P0 需求可以插队，但必须补充事后记录。
5. P1 需求必须有业务负责人确认。
6. P2/P3 需求可按版本节奏统一评审。
7. 被拒绝或暂缓的需求必须记录原因。
```
