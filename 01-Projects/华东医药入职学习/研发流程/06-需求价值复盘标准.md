# 需求价值复盘标准

## 1. 目的

需求价值复盘的核心是回答一个问题：

```text
这个需求上线后，到底有没有产生预期价值？
```

一句话：价值复盘是让需求从“交付闭环”走向“价值闭环”。

## 2. 适用范围

适用于所有 P0/P1/P2 需求，尤其是以下类型：

```text
1. 核心业务流程需求
2. 管理提效类需求
3. 数据报表和看板需求
4. 客户交付类需求
5. 增长转化类需求
6. 降本增效类需求
7. 合规风控类需求
8. 跨部门协作类需求
```

P3 小需求可以轻量复盘，合并到月度需求回顾中统一评估。

## 3. 复盘基本原则

### 3.1 回到最初目标

必须回答：

```text
当初为什么做？
目标是什么？
上线后是否达成？
没有达成的原因是什么？
下一步怎么处理？
```

### 3.2 数据和反馈结合

建议同时看：

```text
1. 使用数据
2. 业务结果数据
3. 用户反馈
4. 业务负责人评价
5. 投入成本
6. 后续问题
```

### 3.3 需求必须有结论

每个需求最终必须有明确结论：

```text
达成预期
部分达成
未达成
无法评估
```

## 4. 复盘时间标准

| 需求类型 | 建议复盘时间 |
|---|---|
| 小功能优化 | 上线后 1-2 周 |
| 核心业务流程 | 上线后 2-4 周 |
| 管理提效工具 | 上线后 4 周 |
| 数据报表/看板 | 上线后 2-4 周 |
| 增长/转化需求 | 上线后 2-6 周 |
| 客户交付需求 | 客户使用 2-4 周后 |
| 合规/风控需求 | 上线后 1 个月或审计节点后 |

## 5. 复盘参与角色

| 角色 | 职责 |
|---|---|
| 产品经理 | 组织复盘，输出价值结论 |
| 业务负责人 | 判断业务问题是否被解决 |
| 数据/BI | 提供使用数据和业务指标 |
| 研发负责人 | 反馈技术成本、稳定性和后续维护成本 |
| 测试负责人 | 反馈质量问题、线上缺陷情况 |
| 客户成功/运营 | 提供用户反馈和推广情况 |
| 管理者 | 判断是否继续投入或调整优先级 |

## 6. 复盘内容标准

### 6.1 原始目标复盘

```text
需求编号：
需求名称：
上线时间：
复盘时间：
原始业务问题：
原始目标：
目标指标：
预期收益：
```

### 6.2 使用情况复盘

| 指标 | 说明 |
|---|---|
| 使用人数 | 有多少目标用户使用过 |
| 使用率 | 使用人数 / 目标用户人数 |
| 使用频次 | 日/周/月使用次数 |
| 功能完成率 | 用户是否完成核心操作 |
| 重复使用率 | 是否持续使用 |
| 放弃率 | 用户在哪一步退出 |

如果目标用户没有使用，先不要急着判断功能无价值，要分析是“不知道”“不会用”“不需要”还是“不能用”。

### 6.3 业务结果复盘

| 目标类型 | 参考指标 |
|---|---|
| 增收 | 转化率、客单价、续费率、成交金额 |
| 降本 | 人工时长、外包成本、客服工单数 |
| 提效 | 审批时长、处理时长、重复录入次数 |
| 控风险 | 错误率、越权次数、审计问题数 |
| 体验 | 完成率、投诉数、满意度 |
| 数据治理 | 数据准确率、缺失率、重复率 |

### 6.4 用户反馈复盘

建议问题：

```text
1. 这个功能是否解决了你的问题？
2. 你是否愿意继续使用？
3. 哪些地方仍然不顺？
4. 是否减少了人工工作？
5. 是否产生了新的操作成本？
6. 是否还有必须优化的问题？
```

反馈分类：

| 类型 | 说明 |
|---|---|
| 正向反馈 | 明确提升效率或体验 |
| 负向反馈 | 功能不好用、不符合流程 |
| 新需求 | 在使用中产生的新诉求 |
| 培训问题 | 用户不会用或不知道 |
| 数据问题 | 口径、准确性、完整性问题 |

### 6.5 投入产出复盘

建议记录：

```text
1. 产品投入人天
2. 设计投入人天
3. 研发投入人天
4. 测试投入人天
5. 上线后修复成本
6. 业务节省或收益
```

| 投入产出情况 | 结论 |
|---|---|
| 低投入，高收益 | 可沉淀为标准能力 |
| 高投入，高收益 | 值得持续优化 |
| 低投入，低收益 | 可保留但不继续加码 |
| 高投入，低收益 | 需要谨慎复盘，避免重复 |

## 7. 复盘结论标准

| 结论 | 判断标准 | 后续动作 |
|---|---|---|
| 达成预期 | 核心指标达到目标，业务反馈正向 | 关闭需求，沉淀经验 |
| 部分达成 | 指标改善但未完全达到目标 | 分析原因，进入优化 |
| 未达成 | 指标无改善或业务不认可 | 调整方案、下线或停止投入 |
| 无法评估 | 缺少数据、埋点或反馈 | 补充数据口径和观察机制 |

## 8. 未达成原因分类

| 原因类型 | 示例 |
|---|---|
| 需求判断错误 | 原始问题并不高频 |
| 目标用户不准确 | 实际使用者不是当初设想的人 |
| 方案设计问题 | 功能做了，但操作成本太高 |
| 推广培训不足 | 用户不知道或不会用 |
| 数据口径问题 | 无法准确衡量效果 |
| 业务流程变化 | 上线后业务规则已变化 |
| 技术体验问题 | 性能慢、稳定性差 |
| 组织协同问题 | 需要多个部门配合但未推动 |

## 9. 不同行业复盘重点

| 行业 | 重点看 | 复盘问题 |
|---|---|---|
| 互联网 | 转化率、活跃度、留存率、点击率、完成率、AB 测试结果 | 用户行为是否变化，转化是否显著提升 |
| SaaS / B 端 | 客户使用率、续费影响、客户满意度、工单数量、关键客户交付 | 客户是否真的用了，是否减少实施和支持成本 |
| 金融 | 风险事件、审批合规率、金额准确率、审计问题、异常操作拦截 | 风险是否降低，审计是否可追溯 |
| 医疗 / 医药 | 流程合规率、审批留痕完整率、研发节点准确率、数据完整性 | 流程是否更合规，数据是否更准确 |
| 制造 / ERP | 库存准确率、单据处理时长、采购交付周期、生产计划准确率 | 是否减少手工对账和跨部门沟通成本 |

## 11. 管理要求

```text
1. P0/P1/P2 需求上线后必须复盘。
2. PRD 中必须提前定义复盘指标。
3. 没有指标的需求，至少要有业务反馈和人工评估。
4. 复盘结论必须进入需求池状态。
5. 未达成需求必须分析原因，不允许简单关闭。
6. 高投入低收益需求必须进入月度产品复盘。
7. 复盘结果要反向影响后续需求优先级。
```
