# M11 方案生成 Copilot：架构决策记录（ADR）

> 本文档记录项目执行前的关键架构决策，避免后续反复讨论。
> 定稿日期：2026-08-19

---

## 决策 1：仓库结构

### 结论

采用 **B 方案：Skill 库和应用独立 repo**。

- `protocol-copilot`：主应用（backend + frontend + worker）
- `protocol-skills`：Skill 规则库（YAML + 医学专家可维护）

### 理由

- Skill 库是核心知识资产，可能由非研发人员维护
- 独立版本发布节奏，不被应用代码发版绑定
- MVP 早期可通过子目录引用或 pip install git+https 方式快速集成

### 集成方式

```
apps/
├── protocol-copilot/          # 主应用 repo
│   ├── backend/
│   │   └── skills/            # 开发时 git submodule 或软链到 protocol-skills
│   ├── frontend/
│   └── worker/
└── protocol-skills/           # 独立 repo
    ├── chapter_1_1_1/
    │   └── v1.0.0.yaml
    ├── chapter_3_1_1/
    │   └── v1.0.0.yaml
    └── _meta/
        └── skill_index.json
```

### 风险与应对

| 风险          | 应对                                            |
| ----------- | --------------------------------------------- |
| 跨仓库版本同步复杂   | 主应用 `pyproject.toml` 中 pin Skill 库 commit/tag |
| 医学专家不习惯 Git | 提供 Web UI 编辑器，后端自动提交到 Skill repo              |

## 决策 2：Skill 版本管理

### 结论

- 每个 Skill **独立语义化版本**（`major.minor.patch`）
- Skill 间依赖通过 `chapter_id` + `min_version` 声明
- `tasks` 表记录任务使用的 Skill 版本组合

### Skill 依赖声明示例

```yaml
skill:
  chapter_id: "3.1.1"
  version: "2.0.0"
  dependencies:
    - chapter_id: "1.1.1"
      min_version: "1.2.0"
```

### 任务表记录示例

```json
{
  "task_id": "task-001",
  "skill_versions": {
    "1.1.1": "1.2.0",
    "3.1.1": "2.0.0",
    "4.1.1": "1.0.0"
  }
}
```

### A/B 测试

- 通过 `skill_versions` 参数控制同一任务使用不同版本
- 生成结果对比后，由医学专家评分决定是否升级

### 回滚策略

- 单 Skill 回滚：修改 `skill_versions` 重新生成
- 全库回滚：主应用回退 Skill repo 的 commit/tag

## 决策 3：异步任务编排

### 结论

采用 **PG jobs 表 + 多 worker 进程竞争消费**。

### 状态机

```
待处理 (pending)
   ↓ worker 抢占
处理中 (running)
   ↓ 成功
已完成 (done)
   ↓ 失败
失败 (failed) → 重试 → 待处理
```

### worker 竞争消费机制

```sql
SELECT * FROM jobs
WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

多个 worker 同时查询时，`SKIP LOCKED` 保证每个 worker 拿到不同任务。

### jobs 表核心字段

```sql
CREATE TABLE jobs (
    id UUID PRIMARY KEY,
    task_id UUID NOT NULL,
    job_type VARCHAR(50),        -- parse / generate / review / render
    status VARCHAR(50),          -- pending / running / done / failed
    payload JSONB,               -- 任务输入
    result JSONB,                -- 任务输出
    attempt INT DEFAULT 0,       -- 重试次数
    max_attempts INT DEFAULT 3,
    error TEXT,
    started_at TIMESTAMP,
    completed_at TIMESTAMP,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);
```

### 重试策略

- 指数退避：`delay = 2^attempt * base_delay`
- 重试次数用尽后标记 `failed`，人工介入

### 扩展路径

- 当前并发不够时 → 增加 worker 进程数
- 未来需要优先级队列/定时任务 → 迁移到 Celery + Redis
- 迁移时业务接口不变

## 决策 4：LLM 网关

### 结论

采用 **B 方案：厚抽象**。

业务模块不直接调用模型，统一通过 `generate(chapter_id, task_id, skill_version, metadata)` 生成。

Prompt 完全由 Skill 定义，网关只负责：

1. 加载指定版本的 Skill
2. 用 Jinja2 渲染 Prompt
3. 调用底层模型
4. 记录调用日志

### 接口设计

```python
class LLMGateway:
    def generate(
        self,
        chapter_id: str,
        task_id: str,
        skill_version: str,
        metadata: dict,
        context: dict | None = None,
    ) -> GenerationResult:
        """泳道 A：章节生成，质量优先"""
        ...

    def extract(
        self,
        input_text: str,
        schema: dict,
        task_id: str,
        context: dict | None = None,
    ) -> ExtractionResult:
        """泳道 B：结构化提取，成本优先"""
        ...
```

### 暂不考虑

- 缓存
- Fallback 降级
- Cost 实时告警

这些功能等日志积累后再做。

### 调用日志落表

```sql
CREATE TABLE llm_calls (
    id UUID PRIMARY KEY,
    task_id UUID,
    chapter_id VARCHAR(50),
    lane VARCHAR(10),            -- A / B
    model VARCHAR(100),
    prompt_tokens INT,
    completion_tokens INT,
    latency_ms INT,
    cost DECIMAL(10, 6),
    created_at TIMESTAMP DEFAULT NOW()
);
```

## 决策 5：人机协作模式

### 结论

采用 **C 方案：混合模式**。

- 高置信度字段：直接用于生成
- 低置信度字段：弹窗/工作台确认后再生成
- 不确定信息：生成时保留 `<占位符>`

### 置信度分级

| 置信度 | 处理方式 |
| --- | --- |
| ≥ 0.9 | 直接使用 |
| 0.7 - 0.9 | 展示给专家，一键确认 |
| < 0.7 | 必须人工填写/修正 |
| 缺失 | 标为占位符 |

### 确认时机

- 阶段一：生成前确认所有中低置信度字段
- 阶段二：根据质量数据调整阈值，减少不必要的确认

## 决策 6：修改痕迹采集

### 结论

采用 **C 方案：Word 修订解析 + Web UI 辅助确认分类**。

### 流程

1. 医学专家在 Word 中修改初稿（使用修订模式）
2. 上传修改后的 Word 文件
3. 系统解析 `w:ins` / `w:del`
4. 将差异片段映射到章节/段落
5. 反馈分析器给出修改原因分类建议
6. 专家在 Web UI 中确认/修正分类
7. 可规则化的修改 → 生成 Skill 补丁
8. 项目特例 → 更新元数据/示例

### 阶段二 MVP 范围

- 先支持段落级文本修订的解析
- 表格、复杂格式的修订暂不支持，标为待处理

## 决策 7：元数据提取

### 结论

采用 **规则引擎 + LLM 增强 + 置信度融合**。

### 规则引擎

- 载体：YAML 规则集（便于医学专家参与维护）
- 能力：正则、关键词、模式匹配
- 负责字段：标题、分期、设计类型、盲法、对照、样本量、入排标准等

### LLM 增强

- 负责字段：给药频率/持续时间、终点评估方法、活动时间表、估计目标五属性
- 输出：JSON Patch 规范化补丁

### 融合策略

```
规则提取器生成初稿
    ↓
对每个字段计算置信度
    ↓
高置信度字段 → 直接采用
中置信度字段 → LLM 校验
低置信度字段（如"未识别"） → LLM 重新提取
    ↓
LLM 输出 JSON Patc
    ↓
融合层合并结果
    ↓
人工确认不确定字段
    ↓
写入元数据库
```

### 输出格式

每个字段输出：

```json
{
  "field": "primary_endpoint",
  "value": "第 16 周 PASI 75 应答率",
  "source": "llm",
  "confidence": 0.85,
  "raw_text": "..."
}
```

## 决策 8：前端策略

### 结论

采用 **C 方案：阶段一即提供最小化 Web 前端，不用 CLI**。

### 阶段一（1-2 月）

- 提供最小化 Web 前端
- 核心界面：
  - 任务列表
  - 上传摘要/IB
  - 事实确认工作台
  - 生成进度（SSE 推送）
  - 下载 Word 初稿
- 事实确认通过 Web 工作台完成

### 阶段二（2-4 月）

- 扩展审阅工作流
- 新增：
  - 修改分类确认界面
  - Skill A/B 测试结果对比
  - 历史任务筛选

### 阶段三（4-6 月）

- 完整审阅工作流 UI
- React + TypeScript + Ant Design
- SSE 推送生成进度
