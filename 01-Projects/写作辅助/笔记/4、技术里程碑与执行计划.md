## 二、技术总原则

1. **MVP 优先**：先跑通 1 个章节，再扩展
2. **抽象可换**：模型层、存储层、部署层必须可替换，不换业务代码
3. **Skill 即资产**：规则库用 Git + YAML 管理，版本化、可审计
4. **日志即证据**：每次 LLM 调用必须落库，支撑成本、质量、合规
5. **占位符即安全**：不确定内容不编造，必须明确标注

## 五、技术启动周（第 1 周）

### 5.1 本周目标

让团队能本地跑起来，P0 技术风险开始验证。

### 5.2 代码/工程任务

| 模块 | 具体工作 | 产出物 | 优先级 |
| --- | --- | --- | --- |
| 项目骨架 | 初始化 Python 项目、FastAPI app、worker 进程 | `pyproject.toml`、目录结构、可启动服务 | P0 |
| 开发环境 | Docker Compose：web / worker / postgres / minio | `docker-compose.yml` | P0 |
| 任务状态机 | `jobs` 表：`解析中 → 待澄清 → 生成中 → 待审阅 → 已完成` | SQL schema + 状态流转 API | P0 |
| 文档解析 | `python-docx` / `PyMuPDF` 读摘要/IB/模板 | 文档解析服务 | P0 |
| M11 模板解析 | 解析标题层级、占位符、条件文本 | 章节树 JSON + 占位符词典 | P0 |
| LLM 网关 v0.1 | 双泳道接口 `generate()` / `extract()`，调用日志落表 | 模型抽象层 + logs 表 | P0 |
| 元数据 Schema v0.1 | 定义核心字段：标题、分期、适应症、设计、人群、干预、终点、统计 | JSON Schema + Pydantic | P0 |
| Skill DSL v0.1 | YAML 格式：metadata、rules、examples、consistency、forbidden、prompt_template | Pydantic 校验工具 | P0 |
| Git 工作流 | Skill 库版本管理、pre-commit | 可提交/回滚的 Skill repo | P1 |

### 5.3 本周要验证的 3 个技术风险

1. **数据合规**：能否调云端 LLM API？如不能，本地模型抽象层是否 ready？
2. **输入格式**：真实方案样本的 PDF/Word 格式差异，解析器能否稳定抽文本？
3. **模型 bake-off**：用同一份摘要 + 同一个 Skill，测 2-3 个模型输出质量。

### 5.4 本周依赖 PM/外部的输入

| 输入 | 用途 | 状态 |
| --- | --- | --- |
| 真实方案样本 5-10 份 | 解析器测试 + 模型 bake-off | 待获取 |
| 医学专家每周 4-8 小时 | Skill 共创 + 质量评审 | 待确认 |
| 数据合规结论 | 决定能否用云端 API | 待法务/IT |
| ICH M11 中英文模板 | 模板解析器输入 | 技术负责下载 |

## 六、阶段一：跑通第一个章节（第 1-2 月）

### 6.1 目标

选择第 **1.1.1 章「主要和次要目的及估计目标」**，实现：

```
摘要 Word/PDF
   ↓ 文档解析模块
纯文本/结构化文本
   ↓ 元数据提取器
结构化元数据 + 置信度
   ↓ 融合层
待确认字段 → 事实确认工作台
已确认字段 → 元数据库
   ↓ Skill 加载
Prompt（元数据 + 规则 + 示例 + 约束）
   ↓ 章节生成引擎
LLM 生成内容
   ↓ 一致性检查器
Issue 清单
   ↓ Word 渲染器
Word 初稿 + Issue 清单 + 生成日志
```

### 6.2 推荐首选章节：1.1.1

理由：
- 摘要中「主要目的」「次要目的」「主要终点」「次要终点」通常齐全
- 估计目标五属性是复杂字段，能验证 LLM 提取能力
- 医学专家盲评容易组织
- 依赖输入少，主要只需摘要

### 6.3 要交付的代码模块

| 模块 | 关键实现 | 参考 |
| --- | --- | --- |

### 6.4 元数据 Schema v0.1 建议字段

```yaml
metadata:
  trial_title: str
  short_title: str
  phase: str
  indication: str
  design_type: str       # 平行组/交叉/析因
  blinding: str          # 双盲/单盲/开放
  control_type: str      # 安慰剂/阳性对照
  sample_size: int
  treatment_duration: str
  interventions:
    - drug_name: str
      dose: str
      route: str
      frequency: str
      duration: str
  population:
    age_range: str
    gender: str
    inclusion_criteria: [str]
    exclusion_criteria: [str]
  objectives:
    primary:
      - objective: str
        endpoint: str
        estimand: dict    # 五属性
    secondary:
      - objective: str
        endpoint: str
  statistics:
    alpha: float
    power: float
    primary_analysis: str
```

### 6.5 Skill DSL v0.1 建议结构

```yaml
skill:
  chapter_id: "1.1.1"
  chapter_title: "主要和次要目的及估计目标"
  version: "1.0.0"
  owner: "医学写作团队"

  required_metadata:
    - primary_objectives
    - secondary_objectives
    - estimands
    - target_population
    - treatment_conditions
    - endpoints

  writing_rules:
    - "先写目的句，使用'本试验旨在评估...'句式"
    - "估计目标按 ICH E9(R1) 五属性描述"

  forbidden_patterns:
    - "不得使用'证明'，应使用'评估'"
    - "不得遗漏伴发事件策略"

  examples:
    - example_id: "oncology_phase3_001"
      content: "..."
      score: 0.95

  consistency_rules:
    - "主要终点必须与第 8 章评估程序一致"
    - "估计目标必须与第 10 章统计方法匹配"

  prompt_template: |
    你是一名医学写作专家，正在撰写 ICH M11 方案的第 {{ chapter_id }} 章。
    
    ## 已知事实
    {{ metadata | to_yaml }}
    
    ## 写作规则
    {% for rule in writing_rules %}
    - {{ rule }}
    {% endfor %}
    
    ## 禁止项
    {% for pattern in forbidden_patterns %}
    - {{ pattern }}
    {% endfor %}
    
    ## 示例
    {% for ex in examples %}
    {{ ex.content }}
    {% endfor %}
    
    请生成本章内容。对不确定的信息，使用 <输入...> 占位符标注，不要编造。
```

### 6.6 阶段一验收标准

### 7.3 反馈闭环数据流

```
AI 生成章节
   ↓
医学专家在 Word 中修改
   ↓
上传修改版
   ↓
解析修订模式 → 差异片段
   ↓
反馈分析器分类
   ↓
人工确认分类
   ↓
├─ 可规则化 → 生成 Skill 补丁 → Git 提交新版本
└─ 项目特例 → 更新元数据/示例
   ↓
回归测试验证质量提升
```
