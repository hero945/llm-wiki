# 统计分析平台：业务与架构深度调研

- 版本：v1.0
- 日期：2026-08-25
- 读者：统计分析平台架构负责人（非医药背景）
- 依据：部门报告《Data Enablement 部门定位与 2026 重点项目（2026.08）》+ 公开行业资料（PHUSE、FDA、CDISC、NMPA CDE 等，见文末参考）

---

## 0. 一页概览

统计分析平台在行业里有一个标准名字：**SCE（Statistical Computing Environment，统计计算环境）**。它要解决的问题不是"装几台能跑 SAS 的电脑"，而是把临床试验统计分析这条**强监管、强质量要求、多角色协作**的生产线，从"散落在个人电脑上的手工作坊"升级为"受控、可追溯、可复用的工厂"。

作为架构负责人，你需要理解的三层逻辑：

1. **业务层**：统计团队的核心产出是 TLF（表格/清单/图），原料是 SDTM/ADaM 标准数据集，加工工具是 SAS（存量绝对主力）+ R/Python（增量），最终产品随新药申报递交给药监局（NMPA/FDA/PMDA），错了会被拒收甚至影响药品获批。
2. **合规层**：全流程受 GxP 监管，平台必须满足"计算机化系统验证（CSV）"、21 CFR Part 11（审计追踪、电子签名、权限隔离）等要求。这是"受控"二字的技术含义，也是架构区别于普通内部工具的根本原因。
3. **平台层**：行业共识的 SCE 能力框架（PHUSE 白皮书）包括——受控数据接入、程序/宏/组件库、任务执行与批处理、版本与差异比较、复核与 QC 工作流、审计留痕、权限与环境隔离。

你们报告里"数据进入—程序执行—结果复核—成果留痕"的最小闭环，正是 SCE 的最小可用切片。

## 1. 业务背景：统计分析到底在做什么

### 1.1 角色与分工

| 角色 | 英文 | 干什么 | 一句话类比 |
|---|---|---|---|
| 生物统计师 | Biostatistician | 设计统计方法、写统计分析计划（SAP）、审阅结果、对专业正确性负责 | 产品经理 + 架构师 |
| 统计程序员 | Statistical Programmer | 用 SAS/R 写程序，把原始数据加工成标准数据集和 TLF | 开发工程师 |
| 数据管理 | Data Manager (DM) | 管理临床数据库（EDC）、数据清理、数据库锁库 | DBA + 数据工程 |
| 医学撰写 | Medical Writer | 写临床研究报告（CSR），引用 TLF 结果 | 技术文档工程师 |

> 术语：SAP（Statistical Analysis Plan，统计分析计划）——在揭盲前就写好的"分析施工图"，规定每个表怎么算、用什么模型。监管要求先定计划再做分析，防止"看数据下菜碟"。CSR（Clinical Study Report，临床研究报告）——新药申报的核心文档。

### 1.2 数据流水线（平台的主数据流）

```text
EDC/外部数据源 (CRF原始数据、实验室、药物警戒等)
        │
        ▼
   SDTM 标准化数据集  ← 收集数据的"标准入库格式"（CDISC SDTM）
        │               申报必交，含 define.xml 数据说明文件
        ▼
   ADaM 分析数据集    ← 为分析优化的派生数据集（CDISC ADaM）
        │               一条受试者记录 = 一行，可直接喂给统计过程
        ▼
   TLF 输出           ← Tables（表）、Listings（清单）、Figures（图）
        │               CSR 正文里的每一个统计表格
        ▼
   CSR / eCTD 申报包  ← 随新药申请递交给 NMPA / FDA / PMDA
```

要点：

- **CDISC**（Clinical Data Interchange Standards Consortium）是临床数据交换的行业标准组织。FDA 和 PMDA **强制要求**按 CDISC 标准递交数据；NMPA CDE 2020 年发布《药物临床试验数据递交指导原则（试行）》，中国申报也已走上这条路。
- **SDTM** 把不同试验收集的数据统一成标准域（如 AE 不良事件、LB 实验室检查、DM 人口学），让审评员和工具都能读懂。
- **ADaM** 是从 SDTM 派生的"分析就绪"数据集，核心原则是**可追溯**：ADaM 的每个值能回溯到 SDTM，SDTM 能回溯到原始数据。平台的"留痕"设计就是在服务这条追溯链。
- **define.xml** 是随数据集一起递交的"数据字典"（XML 格式的元数据说明），审评端用 **Pinnacle 21** 这类校验器自动检查合规性，不通过会被拒收。

### 1.3 质量保证机制（为什么平台要支持这些流程）

- **双重编程（Double Programming / Independent Programming）**：关键分析由两个程序员独立写程序、比对结果，一致才算通过。这是行业 QC 的黄金标准。
- **Proc Compare / 输出差异比较**：SAS 内置的数据集比较过程；结果层面还要比对 RTF/PDF 输出。报告里的首批场景之一"输出差异比较与自动化 QC"就是在把这个手工环节工具化。
- **锁库（Database Lock）**：数据清理完成后冻结数据库，之后的分析结果才有效。锁库前后的数据版本必须严格隔离——平台的版本管理和权限设计要直接支撑这个时间点。
- **专业复核与签字**：统计师复核程序员的产出，复核记录要留痕，作为稽查证据。

### 1.4 这个业务为什么"重"

一次新药申报（NDA/BLA）的统计输出通常是几百上千个 TLF；一个 III 期试验的 SDTM 数据集几十个域、几十万行起步。而且：

- 结果是递给药监局的**法定证据**，错了的代价是审评发补甚至拒批；
- 审评员可能要求**重现分析**，所以几年后还要能用同样的程序、同样的数据跑出同样的结果（可重现性）；
- 稽查（audit/inspection）随时可能来查：谁改的、什么时候改的、为什么改的——没有审计追踪就是重大缺陷。

## 2. 合规约束：架构的"硬边界"

### 2.1 适用框架

- **GxP**：药品全生命周期质量管理规范的总称（GCP 临床试验、GMP 生产、GLP 实验室等）。统计分析属 GCP 范畴，遵循 ICH E6(R2) 等对计算机化系统的要求。
- **21 CFR Part 11**：FDA 电子记录/电子签名法规，是 SCE 合规设计的具体清单：唯一账号、权限控制、**审计追踪（audit trail）**（记录谁在何时对什么数据/程序做了什么，且记录本身不可篡改）、电子签名、记录留存与可读性。
- **CSV（Computer System Validation，计算机化系统验证）**：GxP 系统上线前必须证明"系统按预期工作"并留档（IQ/OQ/PQ：安装确认/运行确认/性能确认）。**平台每次升级都可能触发再验证**，这直接影响发布节奏和架构（例如把"经常变的业务配置"和"不常变的平台底座"分开验证）。
- **NMPA 侧**：GCP（2020 版）同样要求计算机化系统验证与稽查轨迹；《药物临床试验数据递交指导原则（试行）》明确了数据标准化递交要求。

### 2.2 对架构的直接推论

| 合规要求 | 架构含义 |
|---|---|
| 审计追踪不可篡改 | 审计日志走 append-only 存储/独立库，和应用日志分开；时间戳可信（NTP 统一） |
| 账号唯一、最小权限 | 平台级 RBAC + 项目/研究（Study）级数据隔离；禁止共享账号 |
| 记录可追溯、可重现 | 程序、数据、结果、环境（软件版本）四者绑定存档 |
| 系统验证状态受控 | 环境分层（开发/验证/生产），未验证的程序不能碰生产数据 |
| 数据安全 | 受试者数据脱敏（递交数据本身已编码去标识），但仍按敏感数据管理 |

## 3. SCE 是什么：行业共识的能力框架

PHUSE（Pharmaceutical Users Software Exchange，国际药企软件用户组织）2012 年起就定义了 SCE 的标准架构（白皮书 *A Standard Architecture for the Statistical Computing Environment*）。核心思想：**SCE 不是一个软件，而是一个"元数据驱动的受控工作环境"**，由以下能力块组成：

1. **受控数据层**：源数据、SDTM、ADaM 分库分层存储，数据进出都有登记和版本。
2. **程序与组件库**：标准程序、宏（macro，可复用的参数化代码块）、模板统一管理，带版本、状态和所有者。
3. **执行层**：交互式开发 + 批处理执行（batch），任务队列、运行记录、日志捕获。
4. **结果与 QC 层**：输出版本管理、差异比较、复核工作流、签字记录。
5. **元数据与留痕层**：上面一切对象（数据/程序/结果/人员/动作）的关系和变更历史。
6. **治理层**：权限、环境隔离、验证状态、审计报告。

> 元数据驱动 = 平台不是把文件堆在共享盘里，而是知道"哪个程序用了哪个数据集的哪个版本、产出了哪个结果、由谁复核过"。这条知识链是合规和复用的基础，也是平台区别于"共享网盘 + 远程桌面"的本质。

**一个重要的反面教训**（Wright & Barnes 对 Lilly/J&J 等大药企的研究）：SCE 治理有"过度监管（over-regulation）"和"监管不足（under-regulation）"两种失败模式——前者把程序员管死、效率崩溃；后者留不下稽查证据。**一期宁可做薄，不要过早建重型工作流**；先把"能跑、能查、能追溯"做扎实，审批流可以后置。

## 4. 行业方案调研

### 4.1 商业产品

| 产品 | 厂商 | 定位 | 备注 |
|---|---|---|---|
| Life Science Analytics Framework (LSAF) | SAS | 最主流的 SCE：受控内容库 + 版本/审计 + 任务执行 + 电子签名 | 与 SAS 深度绑定，重型、贵，大药企标配 |
| entimICE | Entimo | 全栈临床数据环境（SDTM/ADaM/TLF 全流程 + 合规） | 欧洲系，模块化 |
| Pinnacle 21 Enterprise | Certara | 数据合规校验（CDISC/define.xml），本身不是 SCE 但几乎每个 SCE 都要集成它 | 有免费 Community 版可先用 |
| SAS Viya / SAS 9.4 Grid | SAS | 计算引擎层，不是 SCE | 见 §5.1 选型 |
| R 生态（RStudio/Posit Workbench 等） | Posit 等 | 开源统计计算的企业化托管 | FDA 已接受 R 递交，行业在"去 SAS 单一依赖" |

### 4.2 国内现状

- 国内创新药企（含头部 CRO）主流做法仍是 **SAS 9.4 + 自建共享盘 + 内部 SOP**，部分开始引入 LSAF 或自研轻量 SCE。
- NMPA 数据递交标准化推进后，**国产标准化/校验工具链在补位**（如 SDTM/ADaM 转换、define.xml 生成工具），但成熟的整体 SCE 商业产品国内很少——这正是"自建平台"路线的空间所在。
- 国产化/信创背景下，纯 SAS 方案的采购与维护成本是真实痛点，R/Python 平行能力建设几乎是行业共识。

### 4.3 对你们项目的定位判断

报告口径是"以现有工具和专业资产为基础，重点解决连接、管理、复用和留痕问题"——这对应行业里的**轻量级 SCE 自建**路线（而非采购 LSAF 级重型套件）。这个定位是合理的：一期先服务内部统计团队的标准化场景，用最小闭环验证协作机制。

## 5. 技术架构要点（架构负责人视角）

### 5.1 计算引擎：绕不开的 SAS 决策

- **SAS 9.4**：存量程序的绝对主力（医药行业 30 年积累）。形态有单机（Foundation）、客户端-服务器（EG + Server）、Grid（多节点并行）。许可按核数/模块计费，**成本是架构决策的一等公民**——弹性扩容不能随意，要和许可模型对齐。
- **SAS Viya**：SAS 的新一代云原生平台（容器化、Kubernetes），支持弹性计算，但许可模式和迁移成本需要评估；现有 SAS 9.4 程序大部分可迁移但要验证。
- **R/Python**：用于探索性分析、可视化、新方法（如 Bayesian、机器学习），以及逐步承接部分 TLF 生产。架构上适合**容器化运行**（Docker/K8s），镜像固化 = 环境可重现，天然满足"可重现性"要求。
- **建议形态**：一期"受控服务器 + 远程执行"即可（用户通过网页/瘦客户端提交任务到受控计算节点），VDI（虚拟桌面）可作为受控交互环境的补充选项。决策点：交互式开发体验 vs 受控程度的平衡。

### 5.2 环境分层（行业惯例，合规刚需）

```text
DEV（开发）  →  VAL/QUAL（验证）  →  PROD（生产）
写程序、调通    用测试数据跑验证、    只对锁定数据运行、
随便折腾        双人 QC、UAT 签字     一切留痕、变更受控
```

- 程序和数据在三套环境间**受控晋升（promotion）**，不能随手复制。
- 生产环境的每次变更（程序、宏、配置）走变更控制并留痕。
- 用 **mock/脱敏测试数据**支撑开发与验证，避免真实受试者数据出现在 DEV。

### 5.3 与临床研发数仓的衔接（你们六项工作里的 01 号项目）

报告明确"数据接入与临床研发数仓衔接"。架构上建议：

- 数仓是**唯一数据入口**：平台不直接对接 EDC 等源系统，只从数仓取"稳定、标准化、可追溯"的输入（最好是已经过质量闸门的 SDTM/ADaM 层）。
- 接口形态：受控的数据目录（study → domain → version）+ 只读挂载/快照，平台侧记录"本次运行用了哪个快照"。
- 这是解耦的关键：数仓负责"数据对不对"，统计平台负责"算得对不对、留没留痕"。

### 5.4 任务执行与批处理

- 核心对象：**Task/Job**（程序 + 参数 + 输入数据版本 + 执行环境 → 输出 + 日志）。
- 必备能力：队列与并发控制、运行/停止/**断点重试**、进度查询、日志与清单（SAS 的 .log/.lst）捕获、失败归因（日志解析出 ERROR/WARNING）。
- 批处理场景：一次"全量刷新某 study 的所有 TLF"是真实高频需求，按 study/里程碑组织批任务。

### 5.5 版本、差异比较与自动化 QC（首批场景的直接技术映射）

- **程序/宏库**：Git 是事实标准，但要注意医药行业习惯文件级权限和"已验证状态"标记——Git 管内容历史，平台元数据管"验证状态、所有者、适用范围"。
- **结果版本**：每次运行产出的数据集/RTF/PDF 不可变存储，带运行 ID。
- **差异比较**：
  - 数据集级：SAS Proc Compare 的自动化封装（容差、忽略字段配置）；
  - 输出级：RTF/PDF 文本抽取后 diff，或结构化表格比对；
  - **"输出差异比较"场景的本质 = 回归测试框架**（改了一个宏，重跑受影响的所有输出并比对，报告差异）。这是可以用现代软件工程方法做出亮点的地方。
- **自动化 QC**：日志扫描（ERROR/WARNING/NOTE 规则）、SDTM/ADaM 规则校验（集成 Pinnacle 21 Community 或自研规则引擎）、define.xml 一致性检查。

### 5.6 权限、安全与审计

- 权限模型三轴：**角色**（统计师/程序员/复核人/管理员）× **组织/项目** × **环境**（DEV 放开、PROD 收紧）。
- 数据范围：按 Study 隔离；跨 Study 访问是例外审批。
- 审计：统一审计事件模型（who/when/what/on which object/from which IP），append-only 存储，提供稽查导出报表。
- 账号：对接公司 AD/SSO；禁止共享账号；会话与操作日志留存满足稽查要求。

### 5.7 可复用资产沉淀

- 标准宏库、TLF 模板库、SDTM/ADaM 标准程序，按"草稿 → 审核 → 发布（已验证）"状态机管理。
- 复用的前提是**可发现**：资产目录 + 搜索 + 使用统计（哪些资产被多少项目引用），这是"沉淀复用"定位的技术落点。

## 6. 对照你们报告：四个建设项的技术解读

| 报告建设项 | 技术解读 | 一期建议 |
|---|---|---|
| 1 平台与环境 | 受控计算节点（SAS Server + R/Python 容器）、环境分层、账号权限、审计底座 | 先 DEV/PROD 两档，VAL 用流程代偿；许可测算先行 |
| 2 数据接入 | 与数仓的受控接口：数据目录 + 版本快照 + 只读访问 | 定义"分析就绪数据"的最小契约（study/domain/version） |
| 3 程序与流程 | 程序/宏库（Git+元数据）、任务执行引擎（队列/批处理/重试/日志） | 这是平台骨架，优先做 |
| 4 结果与质量 | 结果版本库、差异比较、QC 规则、复核留痕 | 差异比较 + 日志自动扫描先落地，复核工作流从简 |

首批场景排序建议（从"可标准化程度 × 价值"看）：

1. **SAS 程序/宏及 TLF 自动化**：存量资产最多、最容易标准化，能快速赢得统计团队信任。
2. **输出差异比较与自动化 QC**：纯工程问题，不依赖业务判断，适合 DE 部门独立交付价值。
3. **SDTM/ADaM 程序与说明文档自动化**：价值最高但对数据标准和元数据依赖最深，适合作为一期后半段或二期目标。

## 7. 架构负责人待决策清单

按对一期成败的影响排序：

1. **SAS 许可与部署形态**：9.4 Server 还是 Viya？多少核？并发多少用户？——决定成本上限和弹性空间。
2. **自建 vs 采购的边界**：核心执行/留痕层自建，校验类（P21）用现成，重型工作流一期不做。
3. **环境分层方案**：物理三套还是逻辑三套？晋升（promotion）机制怎么实现？
4. **任务执行引擎**：自研轻量编排（队列+worker）还是引入现成调度（如 K8s Job / Airflow 改造）？注意合规对"运行记录"的要求。
5. **审计与元数据存储**：审计库独立部署、append-only；元数据模型（study/program/run/output/version）早定早受益。
6. **与数仓的接口契约**：数据版本快照的粒度与标识规范。
7. **R/Python 容器策略**：镜像仓库 + 镜像固化（可重现性）+ 包管理白名单。
8. **验证策略（CSV）**：平台自身的 IQ/OQ/PQ 文档责任归属（DE 出技术证据，质量部门签批）——**这个要和 QA 提前对齐，晚了会返工**。
