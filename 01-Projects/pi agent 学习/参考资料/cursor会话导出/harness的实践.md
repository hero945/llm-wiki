## 只需要 LLM + Harness 的工程

Harness(如 Claude Code、Cursor、各类 agent 框架)已经提供了工具调用、文件/shell/浏览器访问、MCP、记忆、循环执行等通用能力。满足以下特征的场景,直接套 harness 就够:

- **人在回路,专家兜底**:用户是开发者/分析师/运维,能审阅中间过程、随时纠正。错误成本由人吸收,不需要系统级保证
- **任务开放、路径不可预知**:写代码、调研、排障、数据探索——你无法预先画出流程图,需要模型自主规划
- **低频、高价值、延迟不敏感**:一次任务跑几分钟没关系,单次产出价值远高于 token 成本
- **工具是通用的**:文件系统、终端、浏览器、MCP 就能覆盖,不涉及企业内部事务系统

典型例子:编程助手、Deep Research、个人自动化、运维 copilot、内容生产流。

## 必须 LLM + 上层 Java/Python 应用的工程

当 LLM 要嵌入一个**对结果负责的生产系统**时,harness 就不够了,你需要传统应用层来提供确定性:

- **确定性约束不能交给概率模型**:计费、权限、合规、审计、数据边界——这些必须用代码保证,不能让模型"大概做对"
- **无人在回路的全自动**:夜间批处理、自动客服闭环、自动下单。没有人兜底,就需要应用层做校验、护栏、重试、回滚、降级
- **高并发/成本敏感**:需要缓存、prompt 路由(大小模型分流)、限流、token 预算控制、批处理——这些是工程问题,不是模型问题
- **深度集成既有系统**:要进数据库事务、调 ERP/CRM、保证多系统间一致性。LLM 只是流程中的一个节点,前后是订单流、审批流、状态机
- **面向终端消费者的产品**:多租户、会话管理、UI、灰度发布、计费,以及可观测性(trace、eval、回归测试)

典型例子:智能客服平台、RAG 知识库系统、审核/风控流水线、AI 功能嵌入现有 SaaS。

## 快速判断框架

问四个问题:

1. **出错了谁兜底?** 人 → harness;系统 → 应用层
2. **流程能预先画出来吗?** 能 → 在应用里编排,LLM 当节点;不能 → harness 让模型自主跑
3. **用户是谁?** 专业人士 → harness;终端消费者 → 应用层包装
4. **有合规/事务/并发要求吗?** 有 → 应用层没得商量

## 实践中的灰度

大多数严肃系统是**混合架构**:上层 Java/Python 应用负责编排、权限、护栏、计费,内部某个环节嵌入一个 agent loop(本质是把 harness 思想作为库引入)。比如客服系统里,会话管理、工单流转、敏感操作审批在应用层,而"排查用户问题"这一步内部跑一个工具调用循环。

一句话总结:**harness 解决"让模型能干活",应用层解决"让系统敢负责"**。探索期用 harness 验证价值,产品化、规模化、合规化的那一刻,就需要上层应用了。

## Harness 的核心特性

### 1. Agent 主循环(Loop)
harness 的心脏是一个 while 循环:模型输出 → 解析工具调用 → 执行 → 结果回填 → 再调用模型,直到模型不再请求工具或触发终止条件。工程上要处理:

- **终止条件**:无工具调用、达到最大轮数、token/时间预算耗尽、用户中断
- **流式输出与可中断性**:用户按 ESC 能立刻打断,且打断后现场可恢复
- **错误即反馈**:工具失败不抛异常崩溃,而是把错误信息作为 tool result 喂回模型,让模型自我纠正——这是 harness 最重要的设计哲学之一

### 2. 工具系统(Tools)
- **工具注册表**:名称 → JSON Schema + 处理函数,描述文案本身就是"教模型怎么用"的 prompt
- **工具即一切**:文件读写、shell、搜索、网页、待办列表、甚至子代理,全部抽象为工具
- **输出治理**:截断(head/tail、字节上限)、超大结果落盘只返回路径、行号标注——保护上下文窗口
- **并发控制**:只读工具并行,写操作串行

### 3. 上下文工程(Context Engineering)
这是 harness 含金量最高的部分:

- **系统提示装配**:身份 + 工具文档 + 环境信息 + 规则文件(AGENTS.md)+ 用户偏好,分层注入
- **压缩与 compaction**:接近上下文上限时,把旧对话摘要化;旧的 tool result 可以单独微压缩
- **渐进式披露(progressive disclosure)**:技能、文档、工具说明按需加载,而不是一次性塞满
- **子代理隔离**:子任务用全新上下文跑,只把结论带回主循环——既省 token 又防止上下文污染

### 4. 权限与安全
- **策略引擎**:工具 × 参数模式 → 允许 / 询问 / 拒绝(比如 `rm -rf` 永远要确认)
- **分级模式**:只读模式、自动接受编辑、全自动
- **沙箱**:容器、git worktree 隔离、OS 级沙箱,让模型"敢跑"

### 5. 会话与记忆
- **会话持久化**:JSONL transcript 记录每一轮,支持 resume、fork、回滚检查点
- **短期记忆**:todo list 作为工具,让模型自己维护任务状态
- **长期记忆**:记忆文件、跨会话偏好

### 6. 可扩展性
- **MCP 客户端**:接入外部工具的标准协议
- **Hooks**:生命周期事件(工具执行前/后)挂载用户脚本
- **Skills / 斜杠命令**:领域知识的插件化

### 7. 可观测性
每一轮的完整 trace、token 计量、成本统计——没有这些,你无法调试和迭代 harness 本身。

## 工程实现:最小骨架

一个 harness 的核心其实可以很小,伪代码如下:

```python
class Harness:
    def __init__(self, llm, tools, policy, budget):
        self.llm = llm
        self.tools = ToolRegistry(tools)   # name -> (schema, handler)
        self.policy = policy               # 权限策略引擎
        self.budget = budget               # token/轮数预算
        self.messages = []

    def run(self, user_input: str):
        self.messages.append({"role": "user", "content": user_input})

        while not self.budget.exhausted():
            response = self.llm.stream(
                messages=self.messages,
                tools=self.tools.schemas(),
                system=self.build_system_prompt(),  # 分层装配
            )

            if not response.tool_calls:
                return response.text  # 模型认为完成,退出循环

            for call in response.tool_calls:
                decision = self.policy.check(call)       # allow / ask / deny
                if decision == "ask" and not self.confirm_with_user(call):
                    result = "User denied this action."
                else:
                    try:
                        result = self.tools.execute(call)
                    except Exception as e:
                        result = f"Error: {e}"           # 错误回填,不崩溃
                    result = self.truncate(result)       # 输出治理

                self.messages.append(tool_result_message(call, result))

            self.maybe_compact()  # 上下文接近上限时压缩

        return "Budget exhausted."
```

## 落地时的关键工程决策

1. **模型无关的核心**:provider 适配层(Anthropic/OpenAI/本地模型),循环逻辑不绑定任何一家
2. **智能放在 prompt 和工具设计里,循环保持"笨"**:不要往循环里塞业务规则;工具描述写得好,比改代码有效得多
3. **一切失败可恢复**:中断、崩溃、上下文溢出,都要能从 transcript 恢复现场
4. **先观测再优化**:从第一天就记录完整 trace,否则你不知道瓶颈在模型、prompt 还是工具
5. **权限是产品功能不是事后补丁**:没有分级权限和沙箱,harness 只能当玩具

## 不要重复造轮子的判断

如果你要的能力 Claude Code / Cursor / OpenHands 已经有(通用编码、研究、运维),直接用或基于它们的 SDK/插件机制扩展;只有当你需要**深度定制**——专有工具链、特殊权限模型、嵌入自有产品、私有化部署——才值得自研 harness。而且自研时,建议从最小循环开始,按上面的清单逐项加能力,而不是一上来复制一个完整 Claude Code。

这也呼应上一条讨论:harness 本身是"让模型能干活"的通用基建,做好之后,它服务的正是那些"人在回路、任务开放"的场景。

## 先定形态：任务式应用，不是聊天机器人

这是最重要的一个判断。这个服务的主交互**不应该做成对话式（chat）界面**，而应该是**任务式（task-based）的结构化交互**。理由：

- 你们的核心交互是"批量确认事实 + 补充缺失字段"，本质是**表单任务**，不是开放探索。chat 适合"我不知道要什么，边聊边明确"，而医学写作人员的目标非常明确：要一份合规的初稿
- 流程是异步长任务（解析几分钟、生成更久）,chat 的线性时间轴承载不了"离开两小时再回来处理"的场景
- 用户心智是"文档和任务"，不是"和 AI 聊方案"

chat 可以作为**局部能力**嵌入（比如某个字段的澄清需要追问时），但不作为主骨架。

## 用户旅程的五个交互时刻

把决策记录里的流程展开，用户和系统的接触点其实是五个：

**1. 创建任务（尽量少问）**
拖拽上传摘要，可选传 IB/历史方案。这里最容易犯的错是创建时问一堆前置问题——不要问，先跑起来，让提取器先干活。用户此刻的耐心应该全部留给后面的事实确认。

**2. 事实确认工作台（核心交互，值得 80% 的设计投入）**
决策记录里写的是"弹窗式对话框"，我建议修正为：**弹窗是容器，但里面不是一串问答，而是一个结构化的确认页**。具体：

- 页面主体是一张**事实表**：所有提取出的字段逐行列出，每行带置信度颜色（绿=高置信、黄=待确认、红=缺失/冲突）
- 绿色字段折叠收起，提供"全部接受"一键操作——用户不该为系统有把握的东西花时间
- 黄色/红色置顶，按你们缺失信息清单里现成的分组组织：基本信息 / 设计 / 人群 / 干预 / 评估 / 统计 / 安全
- **每个问题标注三件事**：来源（摘要原文第几段，可点击高亮原文）、用途（"这个字段支撑第 3、8、10 章")、候选答案（LLM 预生成选项）
- 支持暂存：答了一半可以保存，明天接着答

**3. 生成进度（不打扰）**
章节级进度条（14 章各自的状态），关键是**可离开**——完成后走飞书/钉钉通知（你们技术栈里已经提了这个集成）。生成中不再打断用户提问，所有新发现的问题攒进 Issue 清单。

**4. 交付（Word + Issue 清单，且 Issue 进 Word 批注）**
下载页 = Word 初稿 + Issue 清单 + 生成日志。一个强烈建议：**把 Issue 直接写成 Word 批注**，锚定在对应段落上。这样用户在 Word 里改稿时，系统标记的"此处储存条件缺失""此处与第 8 章剂量不一致"就在手边。这完全符合你们"不强制新编辑器"的决策——把智能送到用户已有的工作流里，而不是拉用户进新界面。

**5. 反馈闭环（极轻，否则没人用）**
上传修改版 → 系统自动 diff + 修改分类 → 用户看到的是一个**带默认分类的确认列表**，默认值全填好，一键提交。分类确认这个环节如果超过 2 分钟，闭环就会断。Skill 补丁确认只在高风险变更时出现，平时不打扰。

## 关键机制：问题分级与交互预算

这是把你们两份文档串起来的核心设计。证据映射分析里有"提取优先级"（高/中/低），决策记录里有"交互触发条件"——把两者映射成**问题三级制**:

- **P0 阻塞级**：高优先级字段缺失（主要终点、样本量、干预方案、设计类型）→ 必须回答，否则不进入生成
- **P1 质量级**：中优先级字段缺失（随机化方法、分析集、DMC)→ 建议回答，可跳过；跳过则该处生成占位符
- **P2 占位级**：低优先级细节（储存条件、剂量调整规则、样本量依据）→ **根本不问**，直接在 Word 里生成 `<输入储存条件>` 占位符

这样做的理由：你们文档里已经明确"保留占位符是安全策略"和"交互补充决定质量上限"——这两条原则之间的平衡点就是分级。**交互预算**建议硬约束：单次澄清不超过 8-10 个问题，多轮澄清最多 2 轮，第二轮只问仍为 P0 的，其余一律转占位符。没有预算约束，澄清循环会无限膨胀，用户会弃用。

配套的成本递减原则：**能把问题做成"确认"就不做成"选择"，能做成"选择"就不做成"填空"**。LLM 应该为每个问题预生成候选答案和默认值，用户大部分时候只在点"对/不对"。

## 贯穿始终的两条原则

**可溯源是交互的一部分，不只是日志。** 合规场景下，用户（和未来的审计方）需要回答"这个数字哪来的"。提取的事实 → 摘要原文段落；生成的段落 → 用了哪个 Skill 版本、哪条元数据。前者在确认页露出，后者在生成日志里可查。

**交互设计的成败标准是"专家时间的占用"。** 这个产品的价值主张是"把空白文档变成可编辑初稿"，对应到交互上就是：医学写作人员在整个流程里花的主动操作时间应该压到 15-20 分钟以内（确认 5 分钟 + 反馈 2 分钟 + 其余是等待）。每个交互设计决策都可以拿这把尺子量。

## 和前两轮讨论的呼应

这正好印证了之前聊的分工：这个项目是典型的 **LLM + 上层应用**——交互是结构化的任务流（状态机：解析中 → 待澄清 → 生成中 → 待审阅 → 已完成），确定性编排、权限、审计都在应用层；而 LLM 只出现在三个"点"上：语义复杂字段的提取、澄清问题与候选答案的生成、章节内容的生成。harness 式的开放自主循环在这个场景里反而是反模式。

## 先看约束（这些决定了 80% 的选型）

- 单团队单用户、内部工具 → 不需要多租户、网关、微服务那一套
- 任务是异步长流程（状态机：解析中 → 待澄清 → 生成中 → 待审阅）→ 需要任务队列和状态持久化
- 输入输出都是 Word/PDF → 文档处理栈必须是 Python 生态
- Skill 是核心资产，Git 管理 → 已决，不进数据库
- 药企数据敏感 → 模型层必须可替换，为私有化留路
- 成本控制"预留不深入" → 调用日志表要有，路由缓存后做

## 后端：Python + FastAPI，没有悬念

整个链路的关键能力——`python-docx`（生成和修订解析）、`PyMuPDF`(PDF 输入）、`docxtpl`（模板填充）、LLM SDK、规则引擎——全在 Python 生态。FastAPI 自带 OpenAPI 文档、原生异步，和前端联调成本低。Java 在这个项目里没有任何理由出现。

真正要做决策的是**异步任务机制**:

- **MVP 推荐**：不用 Celery。直接在 PostgreSQL 里建一张 `jobs` 表（状态、进度、重试次数），起一个独立 worker 进程轮询执行。少一个 Redis 中间件，状态机天然落库，事务性好，单团队完全够用
- **何时升级**：任务并发上来、需要定时任务/优先级队列时，再迁 Celery + Redis，接口不变

状态机显式化：任务表里的状态字段就是交互设计里的那五个状态，前端轮询/SSE 都读它。

## 前端：React + Ant Design，不要炫技

这是数据密集型企业应用（事实确认工作台 = 大表格 + 分组表单 + 置信度标记）,Ant Design 的 Table/Form/Steps/Tag 组件几乎是为这个界面量身定做的，中文企业用户也熟悉这个视觉语言。技术栈：React + TypeScript + Vite + AntD。

两个具体的交互技术决策：

- **进度推送用 SSE 不用 WebSocket**：进度是单向的（服务端→客户端）,SSE 实现简单、自动重连，WebSocket 是杀鸡用牛刀
- **原文溯源高亮**：事实确认页点击"来源"要定位到摘要原文段落——存摘要时按段落切分存偏移量，前端纯文本渲染 + 高亮即可，不要为此引入 PDF 在线预览的复杂度

## 存储：一个 PostgreSQL 打全场

MVP 阶段强烈建议**只有一个存储系统**:

- **结构化数据**（任务、用户、Issue 清单、反馈记录、LLM 调用日志）→ PostgreSQL 普通表
- **提取的元数据（FactBundle)** → PostgreSQL **JSONB** 字段。你们的 metadata schema 还在快速迭代（决策记录里明确说置信度、补丁融合都在演进）,JSONB 让你不用每周改表结构，同时还能用 SQL 查询
- **文件**（原始摘要、生成的 Word、修改版 Word)→ MVP 直接放本地磁盘 + 数据库记路径；私有化部署时换 MinIO(S3 兼容），代码不用改
- **向量数据库 → MVP 砍掉**。历史方案库本来就不在 MVP 范围；真到要做企业知识库那天，优先用 **pgvector**，继续保持单存储系统，别急着上 Milvus/Chroma

Skill 库维持你们已定的方案：Git 仓 + YAML + Jinja2 + Pydantic 校验， Skill 变更触发回归测试可以接 CI。

## 模型：两条泳道 + 用你们的样例做选型测试

这是唯一有真正选型空间的地方，建议分层想：

**泳道 A：章节生成（质量优先）**
长上下文、中文医学写作质量、指令遵循是核心指标。候选：Claude / GPT 旗舰、DeepSeek、Qwen-Max、GLM 这一档。**不要拍脑袋选**——你们手上已有三份样例摘要和抽取结果（secukinumab / ponesimod / peresolimab)，这就是现成的选型评测集：用同一份元数据 + 同一个 Skill，让 3-4 个候选模型各生成一遍第 3 章，用你们已定评估指标里的"结构符合度 + 人工修改比例"打分，半天出结论。

**泳道 B：提取增强 / 修改分类（成本优先）**
这些任务输入短、输出是 JSON，用便宜快速的模型（各家的小号模型）足够。硬要求只有一个：**可靠的结构化输出**(JSON Schema / function calling 支持稳定）。

**MVP 阶段的落地方式**：决策记录说"初期单一模型"——可以，但 LLM 调用层从第一天就按泳道抽象（`generate()` 和 `extract()` 走不同配置），并且**每次调用落库**(task_id、章节、模型、token、耗时、成本），这既满足你们的成本记录决策，也是将来换模型、做路由时唯一可信的数据依据。

**数据合规的退路**：模型层必须做到"换底座不换代码"。现在用企业级 API 跑通，将来药企要求私有化时，能平替成私有化部署的 Qwen/DeepSeek——所以 Prompt 和 Skill 里不要写任何绑定特定模型怪癖的逻辑。

## 部署：Docker Compose 一把梭

MVP 就是四个容器：`web`(FastAPI)、`worker`、`postgres`、（可选）`minio`。单机 Docker Compose 部署，这天然就是将来私有化交付的形态——中国药企场景下，"能离线部署的 Compose 包"比"漂亮的 SaaS 架构"值钱得多。

## 汇总：默认选型清单

- 前端：React + TypeScript + Vite + Ant Design, SSE 推进度
- 后端：FastAPI + 独立 worker 进程， 任务状态机落 PostgreSQL
- 存储：PostgreSQL(JSONB 存元数据）+ 本地文件系统/MinIO;MVP 无 Redis、无向量库
- 文档：python-docx + docxtpl（渲染）+ PyMuPDF(PDF 输入）+ lxml（解析修订 `w:ins`/`w:del`；新版本 python-docx 已支持写批注， Issue 可以直接锚进 Word)
- 模型：LLM 网关抽象两条泳道， 旗舰模型做生成、小模型做提取分类， 全部调用落库； 用三份样例做选型 bake-off
- Skill:Git + YAML + Jinja2 + Pydantic 校验
- 部署：Docker Compose, 即私有化交付物

一句话原则：**MVP 的技术栈要让"换模型、换存储、换部署环境"都不改业务代码**，因为这个项目唯一确定会变的，就是这三样。
