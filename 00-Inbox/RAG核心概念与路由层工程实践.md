# RAG 核心概念与路由层工程实践

> 整理自 2026-08-19 的一次对话：从"为什么需要 RAG"聊到"路由层意图识别的工程经验"。
> 四个递进问题：RAG vs 全量上下文 → 准确度真相 → RAG 不等于向量库 → 路由层怎么做。

---

## 1. 为什么需要 RAG：全量塞文档的四个问题

核心类比：**全量塞文档是把整个图书馆搬进考场，RAG 是先让图书管理员找出相关的几页再进考场**。

| 问题 | 说明 |
|------|------|
| 上下文窗口装不下 | 真实知识库动辄几个 GB，远超任何模型的上下文上限 |
| 成本线性爆炸 | 每次提问都要重新输入全部文档；查询频繁时费用差 100 倍以上 |
| 延迟 | prefill 时间与上下文长度成正比，几十万 token 要等几十秒才出第一个字 |
| Lost in the middle | 模型对超长上下文利用不均匀，中段关键信息易被忽略；噪声越多幻觉越多 |

**全量塞反而更好的场景**：文档量小（几万 token 内）、任务需要全局理解（跨全文推理、总结主线）、查询频率低。

---

## 2. 关键认知：准确度与上下文长度不是单调关系

"全量更准、只是贵"是**错误**总结。真相是一条先升后降的曲线：

- **小语料（远低于上限）**：全量输入更准——没有检索遗漏风险，RAG 的检索错误是纯损失
- **大语料（接近/超过上限）**：全量输入反而更差——注意力稀释 + 噪声干扰；好的 RAG 相当于"降噪"，只留最相关几段，模型答得更准

| | 小语料 | 大语料 |
|---|---|---|
| 全量输入 | 准、贵、慢 | 可能更不准、极贵、极慢，甚至物理不可行 |
| RAG | 有检索误差风险 | 性价比和准确度双赢（前提：检索质量好） |

**术语澄清**："全文检索"（full-text search）是专有名词，指 BM25/Elasticsearch 这类关键词匹配技术，它本身是 RAG 的一种检索手段。想表达的概念应叫"全量上下文 / 长上下文直读"。

---

## 3. RAG ≠ 向量库：检索手段是中性的

RAG 的核心是"检索增强生成"，向量库只是被炒作得最多的一种检索方式。

### 检索方式全景

| 检索方式 | 擅长 | 短板 |
|---|---|---|
| 向量检索 | 语义模糊匹配（"退款"≈"退货"） | 精确匹配差（订单号、人名、ID） |
| ES / BM25 关键词 | 精确词、专有名词、日志 | 不懂语义 |
| SQL / DB | 结构化数据、聚合、精确筛选 | 只适用于已结构化数据 |
| Redis / KV | 确定性键值查找，毫秒级 | 需事先知道 key |
| 图数据库（GraphRAG） | 多跳关系推理 | 建图成本高 |
| 直接调 API | 实时数据（库存、股价） | 依赖外部接口 |

### 两条重要推论

- **"LLM 解析关键字段 → 查 DB/Redis/ES → 喂给模型"是标准做法**，名为 Text-to-SQL / Function Calling / Agentic RAG（LLM 当路由器，自己判断查哪个数据源）。例：客服问"订单到哪了"，正确做法是抽订单号精确查库，而不是把订单库向量化。
- **向量库声量大的原因**：企业约 80% 的知识是非结构化文本（PDF、Wiki、邮件），没法用 SQL 查，向量检索几乎是唯一的语义入口。数据本来就结构化时，完全没必要碰向量库。

### 成熟系统的形态

1. **路由层**：判断问题类型——问事实走 SQL，问流程走向量库，问实时数据调 API
2. **混合检索**：向量 + BM25 同时搜，rerank 合并
3. **生成层**：各路结果拼进上下文综合回答

## 4. 路由层：意图识别的工程实践

路由层是 RAG 系统里最容易被低估、但线上事故最多的地方。

### 四种意图识别方案

| 方案 | 特点 | 适用 |
|---|---|---|
| 规则/正则 | 零成本零延迟，命中部分 100% 准；线上能吃掉 30%~50% 流量 | 订单号、手机号等模式确定的 query |
| 小模型分类器（BERT/fastText） | 毫秒级、便宜；但意图集合外只能瞎猜，加意图要重训 | 意图固定、有标注数据 |
| Embedding 路由 | 免训练、加意图只需加示例句；相近意图阈值难调 | 意图较少、快速搭建（如 semantic-router） |
| LLM 路由 | 零样本、兜长尾、顺便抽实体；有延迟和成本 | 主流选择，可用小一档模型专门做路由 |

### 生产形态：级联漏斗

```text
用户 query
  ├─ 第 0 层：缓存命中？→ 直接返回
  ├─ 第 1 层：规则拦截 → 吃掉高频确定性流量
  ├─ 第 2 层：小模型/Embedding（置信度 > 0.9 直接走）
  └─ 第 3 层：LLM 路由兜底（长尾、模糊、多意图）
```

典型客服系统分布：规则 40% + 小模型 40% + LLM 20%；LLM 层贡献大部分成本，所以持续把 LLM 层高频 case 沉淀成规则/标注数据是日常运营动作。

### 七条踩坑经验

1. **意图和实体一次抽完**：一次 structured output 同时输出 intent + slots，避免两次 LLM 调用
2. **置信度低就澄清，别硬猜**：路由错误是最大失败模式，一次澄清的成本远低于一次错误路由
3. **多意图是常态**：输出 schema 要支持意图列表，底层并行执行后合并
4. **多轮必须带历史**："那什么时候能到？"不看历史无法路由；先做 query rewrite 消解指代
5. **Tool description 就是路由信号**：写清"什么时候用、什么时候不要用"，负面示例比正面示例更管用
6. **路由准确率单独评估**：从线上日志建评估集，每次改 prompt/加工具/换模型都回归一遍
7. **别过度设计**：意图少、量不大时直接 LLM + function calling 一把梭，热点路径再下沉为规则/小模型

## 5. 核心心智模型

- **RAG 的本质**：用任何合适的手段把相关信息弄进上下文；选哪种检索取决于数据形态和问题类型
- **路由的本质**：用最便宜的手段解决最多的 case，把贵的留给真正需要理解力的
- **准确度的本质**：不是"上下文越多越好"，而是"信噪比越高越好"
